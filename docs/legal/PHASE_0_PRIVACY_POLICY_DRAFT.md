## Procedimiento para solicitudes

El proceso futuro sera:

1. La persona escribe al canal de privacidad aprobado.
2. Identifica el correo o los datos sobre los que solicita una accion.
3. El proyecto verifica la identidad de manera proporcional, sin pedir informacion excesiva.
4. La solicitud se clasifica y registra en un medio seguro controlado por el responsable.
5. El proyecto responde dentro de los plazos revisados legalmente.
6. Se completa la consulta, correccion, retiro o eliminacion en los sistemas del proveedor cuando sea necesario.
7. El cierre se documenta sin exponer datos personales en Git, capturas publicas o gestores de incidencias.

Tipos de solicitud: acceso, correccion, actualizacion, eliminacion, retiro de autorizacion, baja de correos, informacion sobre el uso y queja.

```text
Solicitud recibida
→ identidad verificada proporcionalmente
→ solicitud clasificada
→ sistemas del proveedor localizados
→ accion realizada
→ respuesta enviada
→ cierre registrado de forma segura
```

No se debe tratar la informacion de otra persona, incluir listas de contactos en capturas ni almacenar solicitudes en el repositorio. Los plazos y la ruta de escalamiento quedan en `[PENDING_LEGAL_REVIEW]`.

## Ninos, ninas y adolescentes

El producto puede resultar atractivo para estudiantes jovenes. El formulario inicial minimizara datos y no pedira colegio, edad exacta, direccion, telefono ni respuestas sensibles. No se crearan perfiles de publicidad comportamental ni se usara urgencia manipulativa.

El embudo no esta disenado para recopilar intencionalmente datos sensibles de menores. Sin embargo, no se presume que una casilla resuelva por si sola los requisitos aplicables. La edad, el alcance de la autorizacion, la participacion de padres o representantes y el tratamiento apropiado deben revisarse profesionalmente antes de produccion: `[PENDING_LEGAL_REVIEW]`.

No se establece una edad minima en este borrador.

## Seguridad

El proyecto aplicara medidas razonables y proporcionales, sin prometer seguridad perfecta:

- Recoleccion minima.
- Secretos del proveedor solo del lado servidor si se usa una API en el futuro.
- Identificadores publicos de formularios separados de los secretos.
- Entornos de Produccion, Preview y local separados.
- Acceso restringido a cuentas de proveedores.
- Autenticacion fuerte y MFA cuando este disponible.
- Minimo privilegio y revision periodica de accesos.
- Ningun dato personal en analitica, URLs o control de versiones.
- Redaccion de datos ingresados por usuarios en registros tecnicos.
- Ninguna exportacion cruda en Git.
- Exportaciones temporales cifradas o estrictamente controladas.
- Procedimiento de incidentes y revision de acceso del proveedor.
- Datos de prueba identificables y aislados; datos de produccion nunca usados como fixtures locales.

Una falla del proveedor no debe exponer datos de contacto. El PDF debe seguir disponible de acuerdo con el fallback de soft gate aprobado.
